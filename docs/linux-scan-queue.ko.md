# Linux 점검 순차 실행

소스 확인·검증일: **2026-10-02** · [English](linux-scan-queue.en.md)

이 안내는 로컬 개발 소스에 반영한 변경입니다. GitHub 코드 게시, 이미지 재빌드,
운영 Linux 서버 재배포는 이번 검증에 포함하지 않았습니다.

## 사용자가 보는 동작

- 여러 사용자가 소스·라이브러리 점검을 요청해도 서버의 점검 엔진은 한 번에
  하나만 실행합니다. 다른 요청은 DB에 `queued` 상태로 남습니다.
- 수동 점검은 사용자·프로젝트 구분 없이 접수 순서대로 실행합니다. 앞선 대기
  요청이 취소되면 다음 요청으로 넘어갑니다.
- 이미 시작한 예약 점검은 수집·분석·임시 원본 정리를 완료한 뒤 실행권을
  반환합니다. 그 사이에 들어온 수동 점검은 기다립니다.
- 다음 작업을 선택할 때는 기존 수동 우선 정책을 유지합니다. 수동 대기열이
  비면 예약 대상을 기존 예약 시각·설정 순서대로 처리합니다. 수동 요청이 계속
  들어오면 예약 실행이 늦어질 수 있으며, 두 종류를 합친 전역 FIFO는 아닙니다.
- 예약 기능을 비활성화하면 새 예약 실행을 시작하지 않습니다. 이미 실행권을
  확보한 예약은 완료하며, 진행 중인 작업 중단은 별도의 취소 기능을 사용합니다.
- 화면 조회·인증·일반 파일 업로드 같은 HTTP 요청을 모두 한 줄로 묶지는
  않습니다. 수동 GitLab 입력 가져오기는 접수 전 준비 단계이고, 이 변경이
  직렬화하는 대상은 점검 엔진과 예약 수집·분석·정리입니다.

예약 실행 동시성은 기존처럼 `concurrency=1`입니다. 기본 예약 분석 한도는 CPU
1개·메모리 4 GiB, 수집 속도 5 MiB/s, 작업 간 간격 30초이며 운영자가 기존
설정에서 조정합니다. 개별 작업의 자원 사용은 컨테이너/분석기 한도도 적용되므로
순차 실행을 서버 부하가 0이라는 의미로 해석하지 않습니다.

## 복구와 요청 제어

실행 시작은 SQLite 쓰기 트랜잭션에서 다른 수동·예약 실행과 예약 lease를
재확인합니다. 수동 워커는 DB의 대기 요청을 계속 확인하므로 시작이 보류돼도
요청을 잃지 않습니다. DB별 파일 잠금으로 복구·수동 워커의 소유자를 하나로
제한하며, 기존 소유자가 종료하면 보조 워커가 대기 작업을 이어받습니다.

GitLab 예약 아카이브 전송은 동시에 한 건만 허용합니다. 아카이브 전송 슬롯과
작은 제어 API 슬롯을 분리해 다운로드 중에도 상태 확인·취소를 처리하며,
아카이브 전송이나 결과 업로드를 무제한 병렬화하지 않습니다. 인증·lease 검사와
기존 본문 크기 제한은 유지합니다.

이번 문서 게시에는 구현·테스트 파일이 포함되지 않습니다.

```bash
PYTHONPATH=platforms/shared/python python3 -m unittest discover -s tests -q
PYTHONPATH=platforms/shared/python:tests python3 -m unittest test_scan_serialization -q
```

- 전체 Python: **623개 중 616 통과·7 건너뜀**, 실패·오류 없음(70.018초).
- 순차 실행 회귀: 11개 통과. 별도 DB 연결의 경쟁, 사용자별 FIFO, 예약 실행
  중 수동 대기·정리 후 재개, 취소 상태, 중복 워커·소유권 인계를 검증했습니다.
- 느린 GitLab 전송 중 heartbeat 성공·두 번째 아카이브 거부, 예약 수집 도중
  새 수동 요청이 들어와도 API/기존 워커가 완료되는 경로도 통과했습니다.
- 기존 삭제 UI 테스트는 CSS 선택자 문자열 대신 실제 HTML 요소를 검사하도록
  바로잡았습니다. UI·삭제 권한의 제품 동작은 이 교정으로 변경하지 않았습니다.
- 건너뜀: macOS 환경에서 Linux 전용 6개, Playwright 없는 PDF 렌더러 1개.
- 이 Mac의 Docker daemon이 실행되지 않아 실제 Linux 컨테이너 배포·Linux 전용
  테스트는 실행하지 못했습니다. 실제 GitLab 서버도 사용하지 않은 fixture 검증입니다.
