# KODA Linux 서버 안정화 실행안

작성일: 2026-10-02. 현행화: 2026-10-11. 설계 검토 후 사용자가 승인한 우선순위 1·2·3을 로컬 소스에 구현했다. 운영 서버의 실행 이미지, CPU/RAM, 데이터 규모와 실제 지연은 아직 측정하지 않았으며 서버 배포·파일 삭제는 수행하지 않았다. 기존 미커밋 변경은 유지했다.

## 2026-10-11 실제 실행 검증

현재 소스를 Debian 12·Python 3.12.15의 `linux/amd64` 시험 이미지에서 실행했다.
Apple Silicon의 Docker LinuxKit VM에서 amd64 사용자 공간을 에뮬레이션한 결과이며
물리 x86_64 서버나 네이티브 x86_64 커널의 성능·호환성 검증은 아니다.

- 전체 회귀: 768개 중 767개 통과·실패 0개·로컬 LLM 연동 1개 건너뜀(198.051초).
- `platforms/linux/install.sh --no-link` 소스 설치본과 CLI·PDF·미인증 포털 API 거부 확인.

  `log4j-core 2.14.1` JAR에서 취약점 7건·경고 0건, `--fail-on high` 종료 코드 1.

재실행했다. 이번 GitHub 게시에는 제품 소스·테스트·빌드 스크립트와 문서를 포함하며 이미지·운영 배포는 포함하지 않는다.

## 구현한 우선순위 1·2·3

이 구현 범위는 아래 세 항목이다. 뒤에 남긴 원인 조사와 장기 운영 로드맵은 구현 전 관찰 및 후속 제안이며, 모두 구현됐다는 뜻은 아니다.

| 우선순위 | 구현 결과 | 주요 파일 |
|---|---|---|
| 1. 임시 작업 공간 수명 관리 | 일반 파일은 압축 해제 폴더를 만들지 않는다. 아카이브만 회차 ID와 소유권 잠금이 있는 임시 폴더를 사용하며 완료·실패·취소·시간 초과 시 분석 프로세스 종료를 확인한 뒤 정리한다. 종료 확인 실패 시 작업 공간과 실행 상태를 보존한다. 워커 시작 시 잠기지 않은 기존 잔여 폴더도 회수한다. | `portal_workspace.py`, `portal_worker.py`, `linux_portal.py` |
| 2. 화면·DB 경량화 | 대시보드는 저장된 요약만 조회한다. 이력·취약점은 서버에서 페이지를 나누고 상세는 선택 시 읽는다. 상태 전용 API와 응답 후 재예약 polling을 사용한다. 변경 없는 사용자 인증은 DB 쓰기를 하지 않고 결과 직렬화는 쓰기 트랜잭션 밖에서 수행한다. | `portal_store.py`, `portal_views.py`, `linux_portal.py` |
| 3. 분석·외부 게시 분리 | 웹, 분석 워커, Tracker/GitLab 전송 워커를 같은 이미지의 별도 컨테이너로 실행한다. 분석은 별도 자식 프로세스에서 실행하며 취소·deadline·프로세스 그룹 정리를 적용한다. 외부 재전송 요청은 영속 대기열에 접수 후 202로 응답한다. 보고서는 단일 슬롯의 자식 프로세스로 생성한다. | `portal_worker.py`, `portal_reports.py`, `cli.py`, Linux 설치 스크립트 |

압축 입력에는 기존 분석기의 경로 기반 입력이 필요하므로 분석하는 동안 임시 추출 폴더가 존재한다. 전체 압축 해제 제거, 선택 추출, 분석 캐시 및 중복 분석 제거는 후속 범위다. 이번 변경은 점검 결과와 원본 보존 계약을 유지하면서 폴더 누적과 웹 경합을 줄인다.

기존 회차의 요약은 분석 워커가 유휴 시간에 한 회차씩 채운다. 집계가 끝나기 전에는 대시보드에 `집계 중`을 표시하며 첫 화면 요청에서 전체 과거 결과를 읽지 않는다. 전체 보고서와 기존 전체 결과 API는 모든 취약점을 보존한다. 취약점 페이지 조회는 아직 SQLite JSON 배열을 검색하므로 매우 큰 단일 결과의 검색 비용은 남는다.

설치·재설치·업데이트는 기존 `koda-suite` 흐름에서 웹과 두 워커를 함께 관리한다. 컨테이너 재생성에는 기존 포털 데이터 마운트를 사용한다. 정상 종료 중인 분석은 입력을 보존하고 대기열로 돌려놓는다. 갑작스러운 종료의 수동 회차도 재시작 시 대기열로 복구하며 이미 취소 요청이 있으면 취소로 확정한다. 예약 회차는 기존 lease·복구 정책을 유지한다. 정리에 실패하면 감사 기록을 남기고 분석 워커를 중단하여 추가 임시 폴더 누적을 막는다. 프로세스 그룹 종료 실패 시 `scan.termination_failed`를 기록하고 실행 상태·작업 공간을 보존하며 다음 분석을 시작하지 않는다. 초기 PermissionError의 원인은 확정하지 않았으며 프로세스 그룹이 사라졌음을 확인할 때만 종료 경쟁으로 허용한다. 명시적인 reset-install은 기존과 같이 데이터 삭제 절차다.

기본 자원 설정은 분석 워커 1 CPU/4 GiB, 전송 워커 0.5 CPU/512 MiB, 분석 제한 시간 21,600초, 종료 유예 3초다. 설치된 `tracker/.env`의 `KODA_SCAN_CPUS`, `KODA_SCAN_MEMORY`, `KODA_DELIVERY_CPUS`, `KODA_DELIVERY_MEMORY`는 컨테이너 자원 상한이며 분석 자식의 기본 1 CPU/4 GiB 상한도 적용된다. `KODA_SCAN_TIMEOUT_SECONDS`, `KODA_SCAN_TERMINATE_GRACE_SECONDS`로 분석 시간을 조정한다. 분석 워커는 네트워크 없이 실행하며 외부 전송 설정은 전송 워커에 전달한다. heartbeat 검사에는 DB 초기화나 쓰기가 필요 없다. 예약 결과의 전송도 전송 워커로 이동하며 기존 정리 완료 조건과 재시도 간격을 유지한다.

보고서는 웹 컨테이너 안의 별도 자식 프로세스이므로 웹과 같은 Docker 메모리 한도를 공유한다. 동시 생성 1개, 기본 deadline 90초, Linux CPU 제한과 메모리 예산을 적용한다. PDF는 Chromium의 큰 가상 주소 공간을 허용하고 0.2초 간격으로 분리된 브라우저까지 실제 RSS를 확인한다. 기본 예산은 2 GiB이며 이 검사는 커널의 강제 상한이 아니다. [V8 가상 메모리 구조](https://github.com/v8/v8/blob/main/docs/heap/pointer-compression.md), [Playwright 브라우저 실행 방식](https://github.com/microsoft/playwright/blob/v1.55.0/packages/playwright-core/src/server/utils/processLauncher.ts#L126-L136)을 고려한 처리다. 보고서 자체를 별도 컨테이너로 옮기는 것은 후속 작업이다. 2026-10-11 amd64 시험 컨테이너에서 실제 Chromium PDF와 컨테이너 자원 설정을 확인했다. 강제 OOM 복구와 운영 연동은 미검증이다.

검증 근거: `tests/test_portal_worker_runtime.py`, `tests/test_portal_store_performance.py`, `tests/test_portal_pagination.py`, `tests/test_portal_worker_packaging.py`. 실제 자식 프로세스의 완료·취소·timeout·종료 복구, CPU 부하 중 HTTP 응답, 보고서 timeout 중 상태 조회, 전체 결과를 읽지 않는 목록·집계, 권한 및 설치 수명주기 계약을 검사한다.

2026-10-02 로컬 합성 DB 측정(이전 기록): 완료 회차 100개, 회차당 취약점 500개와 1,280바이트 문맥을 저장한 경우 기존 전체 결과 조회 방식의 중앙값 99.24ms → 요약 조회 24.29ms였다. 요약 반환량은 2,084바이트이며 단일 전체 결과는 676,404바이트였다. 같은 데이터의 3회 warm 측정으로, 실제 서버나 브라우저 성능 보장이 아니다.

2026-10-02 회귀 검증(이전 기록): `PYTHONPATH=platforms/shared/python:tests python3 -m unittest discover -s tests -q` → 682개 검사, 675개 통과·7개 건너뜀, 실패 없음(89.444초). 변경 Python 모듈의 `py_compile`, Linux launcher의 `bash -n`, 범위별 `git diff --check`도 통과했다. 당시 Docker daemon이 연결되지 않아 실제 컨테이너 실행은 포함하지 않았다. 현재 실행 결과는 위 2026-10-11 구간을 기준으로 하며 OOM 복구와 운영 서버 성능은 여전히 미검증이다.

## 목표와 원칙

점검이 오래 걸리거나 실패해도 로그인, 페이지 이동, 결과 조회, 작업 취소가 응답해야 한다. 점검 속도는 대기 시간·수집·압축 해제·분석·저장·외부 게시로 나눠 개선한다. 분석 결과와 규칙 범위를 줄여 얻은 속도 개선은 성능 개선으로 인정하지 않는다.

기존 전역 단일 점검 실행권, DB 대기열, 권한 검사, 출처 검증, 업로드/압축 해제 한도를 유지한다. 처음부터 동시 점검 수를 늘리거나 DB·웹 프레임워크를 한꺼번에 교체하지 않는다.

## 권장 실행 구조

```text
브라우저 → Gateway / 인증 → Web·조회 API → 작업 상태·요약 DB
                               ↓ 작업 접수 / 취소
                         영속 점검 대기열
                               ↓ 단일 실행권
                       별도 분석 워커 / 자식 프로세스
                               ↓ 결과 확정
                         영속 외부 전송 대기열 → Tracker / GitLab

보고서 생성도 별도 제한된 작업 슬롯에서 수행
```

웹은 접수·조회·권한·취소를 담당하고 압축 해제, 파일 수집, 분석, 대형 보고서 생성은 격리한다. 수동·예약 모두 기존 단일 실행권 계약을 공유한다. 외부 전송은 점검 실행권을 잡지 않는다. 워커를 분리해도 동일 호스트의 디스크와 메모리는 공유하므로 각각의 한도와 호스트 여유를 함께 설계한다.

### 0단계 — 측정 기준과 회귀 계약 확보

- 운영 이미지 digest·설정·DB 스키마와 로컬 소스의 일치 여부부터 확인한다.
- 요청 ID와 run ID를 연결하고 endpoint별 p50/p95/p99, 인증 upstream 시간, DB 잠금 대기, SQL 시간, 응답 크기를 기록한다. 소스 내용·쿠키·토큰은 로그에서 제외한다.
- 점검 단계별 시간, 대기열 길이/최고 대기 시간, CPU throttling, RSS, OOM, I/O 대기, 디스크/ inode 여유, 임시 공간, 워커 heartbeat를 수집한다.
- 유휴, 분석 중, 결과 저장 순간, PDF 생성 중을 따로 비교한다. 서버 TTFB와 브라우저 렌더 시간을 분리한다.
- 취소·중복 실행·권한 철회·재시작 복구·완료 결과 불변성에 대한 회귀 테스트를 확보한 다음 구현한다.

### 1단계 — 화면과 제어 기능 응답성 확보 (P0)

1. **조회 경량화:** 대시보드에는 회차별 요약·집계만 조회한다. 이력은 서버측 페이지네이션/정렬/필터로 바꾸고 목록 SQL에서 result_json을 제외한다. 최신 회차·상태·프로젝트 조회 인덱스는 실제 query plan으로 선정한다. 상세 findings도 페이지 단위로 제공한다.
2. **DB 쓰기 단축:** 기존 사용자 조회는 읽기 경로로 처리하고 최초 등록/실제 표시명 변경에만 쓴다. 권한·차단 상태 검사는 유지한다. 결과 JSON은 트랜잭션 밖에서 직렬화한 뒤 상태를 재확인하고 짧게 commit한다. 대형 결과 중복 저장은 revision 계약을 보존하는 이관안을 별도로 둔다.
3. **SQLite 조정:** 로컬 디스크에서 WAL·checkpoint·짧고 제한된 busy 처리 방식을 실험한다. WAL은 writer를 여러 개로 만들지 않으며 Python 공용 잠금도 해소하지 않는다. 네트워크 공유 디스크에 WAL DB를 두지 않는다. DB 이전은 경합 측정 결과가 요구할 때 후속 검토한다.
4. **분석 격리:** 예약 분석기의 자식 프로세스 관리 패턴을 재사용하여 수동 분석도 웹 프로세스 밖에서 실행한다. 다음으로 워커 컨테이너를 분리해 CPU·RAM·PID 한도를 독립 적용한다. 분석기 OOM이 웹 컨테이너 OOM으로 이어지지 않는지 검증한다.
5. **실제 취소:** `cancelling`과 `cancelled`를 구분한다. 단계별 협력 취소, 전체 deadline, 프로세스 그룹 TERM→유예→KILL, 자식 프로세스 회수·임시파일 정리 후 실행권 반환을 구현한다. 취소와 완료가 경합해도 한 번만 최종 상태가 정해져야 한다.
6. **요청 보호:** 업로드·PDF·외부 연동·일반 조회의 동시성/크기/시간 한도를 분리한다. 제어 요청용 처리 용량을 남기고 과부하는 빠른 429/503과 재시도 안내로 반환한다. 인증 실패를 우회하는 fallback은 넣지 않는다.
7. **자동 복구:** dashboard restart 정책, graceful shutdown, 새 작업 접수 중단과 drain, 워커 heartbeat·lease 만료 감지를 추가한다. healthcheck 실패가 곧 컨테이너 자동 재시작을 의미한다고 가정하지 않는다.

### 2단계 — 점검 처리 시간과 화면 체감 속도 개선 (P1)

- **외부 전송 분리:** 결과 확정과 같은 트랜잭션에서 outbox를 기록하고 별도 전송 워커가 제한된 재시도·지수 backoff를 수행한다. run/revision/destination 기반 멱등성을 보장하고 응답 유실 시 기존 원격 결과를 확인해 중복 이슈/게시를 막는다.
- **수집·업로드 비동기화:** 원본 업로드 후 검증·해제·GitLab 다운로드를 작업으로 처리한다. 접수 응답에 job ID를 반환하고 페이지 이동 후에도 진행 상태를 다시 찾을 수 있게 한다. 이중 클릭·새로고침 재전송은 idempotency key로 제어한다.
- **안전한 캐시:** 입력 해시뿐 아니라 분석기·규칙·설정·취약점 DB 버전을 캐시 키에 포함한다. 의존 관계에 영향을 받는 소스 규칙은 단순 파일별 증분 분석을 적용하지 않는다. 권한별 데이터 격리와 삭제 시 무효화를 지킨다.
- **중복 작업 제거:** 동일 입력의 파일 순회·압축 해제·라이브러리 목록 생성을 가능한 범위에서 공유한다. 단계 프로파일링 후 병렬화 가능한 분석만 제한적으로 늘린다. 전체 점검 동시성은 우선 1을 유지한다.
- **UI:** 전체 결과를 HTML/스크립트에 싣지 않고 필요한 페이지·상세만 읽는다. 상태 polling은 응답 후 재예약하여 겹침을 막고 숨은 탭은 늦춘다. 대량 DOM을 줄이고 정적 asset에는 버전 기반 캐시를 사용한다. 사용자별 결과 HTML은 공유 캐시하지 않는다.
- **진행 표시:** 대기 위치/대기 시간/현재 단계/마지막 갱신을 표시한다. 고정 퍼센트는 실제 처리량처럼 표현하지 않는다. 연동 실패와 분석 실패, 부분 분석을 구분한다.
- **공정성:** 수동 FIFO는 유지하면서 예약의 최대 대기·aging 정책을 도입할지 결정한다. 사용자·프로젝트별 대기열 한도, 전체 대기열 상한, 예약 겹침·재부팅 후 누락 실행 정책을 명시한다.

### 3단계 — 장기 운영 및 배포 복구 (P1/P2)

- 입력·압축 해제·보고서·DB·로그에 각각 저장량 예산과 보존 정책을 둔다. 디스크/inode가 임계치에 도달하면 새 대형 작업을 차단하고 조회·취소에 필요한 공간을 보전한다. 활성 작업과 미전송 결과는 자동 정리에서 제외한다.
- 로그 회전, 주기적인 만료 파일 정리, 실패 정리 작업 재시도, 취약점 DB 갱신 중 버전 고정 및 원자 전환을 검증한다.
- SQLite online backup 또는 일관된 정지 백업과 업로드/결과 artifact manifest를 묶는다. WAL 사용 시 DB 파일만 복사하지 않는다. Tracker DB·설정·권한·암호화 키의 복원 절차도 함께 검증한다.
- 초기 복구 목표 제안: RPO 24시간·RTO 1시간. 실제 업무 요구와 데이터량으로 확정하고 별도 환경에서 복구 훈련한다.
- 새 이미지 사전 검증 → 짧은 접수 중단 → DB 백업 → 호환 migration → 배포 → 실제 로그인/조회/fixture 점검 → 문제 시 롤백 순으로 릴리스한다. 스키마 변경 후 구버전 이미지 롤백 가능 여부를 먼저 정의한다.
- 현 `ThreadingHTTPServer`의 운영 한계를 고려해 성숙한 HTTP serving 계층으로의 점진적 이전을 후속 과제로 둔다. 프레임워크 교체만으로 분석 격리와 DB 경합이 해결된다고 가정하지 않는다. 신규 의존성은 별도 결정 대상으로 둔다.

## 검증 기준과 부하 시험

아래 수치는 성능 보장이 아니라 초기 합격 목표다. 실제 서버 스펙·동시 사용자·최대 입력에 맞춰 고정한다.

| 항목 | 초기 목표 |
|---|---|
| 상태·취소 접수 API | p95 500ms 이내 |
| 목록·대시보드 API/HTML 서버 응답 | p95 1초 이내, 브라우저 주요 내용 표시 2초 이내 |
| 점검 부하 중 응답 | 위 기준 충족 및 유휴 대비 p95 악화 2배 이내 |
| 실제 취소 종료 | TERM 유예 포함 10초 이내, 초과 시 강제 종료·정리 상태 표시 |
| 포화 상황 | 조용한 멈춤 대신 bounded 대기 또는 명시적 429/503; 정상 부하 5xx 0.1% 미만 |
| 분석 정확성 | 동일 fixture·규칙·DB 버전에서 finding/범위 보존, 부분 실패를 완료로 오표기하지 않음 |
| 장기 실행 | 최소 24시간 soak 후 자원·임시파일 지속 증가 없음 |

1. 소형/중형/대형 fixture와 100/1,000/10,000회 이력, 큰 findings 데이터셋을 만든다.
2. 1/5/20 동시 사용자에서 조회·새 점검 접수·취소를 섞는다. 최고 지원 규모를 넘는 구간은 성능 목표가 아니라 과부하 처리 시험으로 분리한다.
3. 분석·결과 저장·대형 업로드·PDF·연동 지연을 각각 겹쳐 병목을 분리한다.
4. 워커 kill, timeout, OOM, DB 잠금, 디스크 부족, 네트워크 실패, 서버 재시작을 격리된 Linux 시험 환경에서 주입한다.
5. 변경 전후 동일 데이터·이미지 조건으로 p95/RSS/처리 시간을 비교한다. 실서버에서 파괴적 부하/장애 주입은 하지 않는다.

- 강제 종료·OOM·호스트 종료나 파일 권한/파일시스템 문제는 정리를 막을 수 있다. `portal_store.py:1738–1794`의 재시작 복구는 회차 상태와 원본 입력을 처리하지만 `work/koda-portal-*` 잔여물 정리 경로는 확인되지 않았다.
- 실행 중 폴더는 삭제 대상이 아니다. run ID/워커 소유권·lease·heartbeat와 연결해 미사용임을 검증한 폴더만 회수해야 한다. 현재 이름에는 run ID가 없으므로 시간만 기준으로 하는 삭제보다 작업 디렉터리 소유권 기록을 먼저 추가하는 것이 안전하다.
- `TMPDIR`만 바꿔도 해결되지 않는다. 포털은 TemporaryDirectory에 `dir=work_root`를 명시한다. 현재 Docker 기본 `/tmp` tmpfs도 512 MiB이므로 최대 4 GiB 해제 작업을 통째로 옮길 수 있다고 가정하지 않는다.

### 라이브러리 분석에서는 전체 해제를 줄이는 방향

| 입력/범위 | 권장 처리 | 필수 검증 |
|---|---|---|
| 라이브러리 전용 ZIP/TAR 프로젝트 | archive member 목록에서 지원 manifest/lockfile만 읽는 스트림 분석; 실제 파일 경로가 필요한 경우에만 선택 추출 | manifest/lockfile의 하위 경로·여러 프로젝트·우선순위·같은 이름·대형 파일·제외 규칙 처리 동일성 |
| JAR/WAR/EAR 바이너리 | 기존 Java archive reader로 pom.properties/manifest와 중첩 라이브러리를 bounded 메모리에서 읽음; 외부 분석기는 지원되는 원본 파일 입력 활용 | 중첩/음영처리된 라이브러리·해시·위치·식별·SBOM·부분 분석 상태 보존 |
| 소스/전체 점검 | 기존 경로 기반 분석기가 필요로 하는 파일만 임시 추출, 작업 종료 후 정리 | 프로젝트 전체 맥락·경로·규칙·제외/ignore 의미 보존 |
| 해제 불필요한 일반 파일 | 원본 직접 읽기, 빈 임시 폴더 생성 생략 | 단일 파일 점검 범위 보존 |

현재 Linux 포털은 일반 `SecurityScanner`와 `dependency_inventory.py:28–59`의 manifest/lockfile 분석 경로를 사용한다. 별도 Java 엔진의 `java_archives.py`와 `syft_adapter.py`에는 원본 archive 입력 지원이 있지만 포털 라이브러리 경로에 자동으로 연결되어 있지 않다. **압축 해제만 제거하면 구성요소가 누락될 수 있으므로**, inventory와 결과 형식·검증을 함께 연결해야 한다. 메모리에서 읽어도 압축 해제 CPU 비용은 존재하며 디스크 쓰기·재탐색을 줄이는 효과를 목표로 한다. 스트림 분석도 누적 바이트·member 수·깊이·압축 팽창·경로 검증 한도를 유지한다.

### 속도 개선 우선순위 보강

1. **화면 이동:** 요약 조회, 서버측 페이지네이션, 상태 전용 API로 전체 이력·결과 읽기를 제거한다.
2. **라이브러리 점검:** 전체 압축 해제/전체 파일 순회를 manifest·archive 메타데이터 선택 읽기로 줄인다.
3. **Grype 중복 실행:** `server.py:271–303`에서 CVE match마다 `_resolve_final_version`을 호출하는 반복을 제거한다. 같은 패키지·후보 버전 검증은 DB/분석기 버전에 묶어 공유하고 batch PURL로 조회한다. CVE별 수정 버전 집합과 최종 상태는 보존한다.
4. **재점검:** 파일 해시·분석 범위·규칙/설정·엔진 버전으로 inventory를 재사용하고, 취약점 비교는 pinned DB 버전으로 별도 캐시한다. DB 변경 시 전체 파일 해제 없이 inventory로 다시 비교한다. 권한별 격리·용량 한도·보존 정책을 적용한다.
5. **자원과 대기:** 분석/전송/보고서 격리로 화면 응답을 확보하고, 프로파일링 후 단계별 제한 병렬화를 적용한다. 워커 격리는 한 작업의 완료 시간을 자동으로 단축하지는 않는다.
6. **보고서 소스 재읽기 제거:** `reporting.py:2978–2991,3158,3244`에서 한국어/영어 payload를 만들 때 finding별로 파일 전체를 다시 읽는 비용을 줄인다. 회차별 파일 읽기·문맥 계산을 공유하고 기존 `stored_source_contexts` 인자를 활용한다. 파일 크기·캐시 바이트 한도와 비밀정보 마스킹을 보존한다.

### 이번 추가 확인

- 작은 ZIP fixture로 실제 `_run_scan`의 입력 준비·상태 저장을 실행하고 분석 함수만 mock했다. 정상 완료·분석 예외 모두 실행 중 임시 폴더 1개 → 종료 후 0개를 확인했다.
- 자식 프로세스가 TemporaryDirectory에서 `os._exit(0)`으로 즉시 종료하는 fixture는 폴더 1개를 남겼고 `recover_incomplete_runs()` 뒤에도 1개였다. 이는 잔여물 회수 공백의 로컬 재현이며 운영 OOM의 원인 확정은 아니다.
- 기존 단일 JAR 직접 분석·SBOM 생성·Syft file-source 계약 테스트 3개 통과(0.005초). Syft 호출은 mock이므로 실제 외부 도구 성능/커버리지 검증은 별도로 필요하다.
- 이번 추가 작업은 문서 보강과 로컬 fixture 확인이며 제품 코드·운영 서버 폴더는 변경하지 않았다.

## 배포 후 저장 공간 정리 — backups / tracker/images

- `tracker/images/*.tar`는 설치 시 `docker load`하는 이미지 반입 원본이다. 정상 실행·suite start/status는 이 tar를 읽지 않고 Docker에 등록된 이미지를 사용한다 (`security-sbom-dependecy/scripts/install-airgap.sh:63–96`, `platforms/linux/suite/koda-suite:688–706`). 필요한 모든 이미지가 Docker에 있고 동일 릴리스 원본을 외부 저장소에서 다시 가져올 수 있으면 설치 경로의 tar 사본은 정리할 수 있다. Docker 저장소에서 이미지 자체를 삭제하는 작업과는 다르다.
- tar를 지운 설치 트리는 완전한 배포 번들이 아니다. 해당 파일이 manifest에 포함되어 있으므로 설치 트리 자체의 전체 checksum 검증/재반입에 사용할 때는 원본을 복원해야 한다. 원본 릴리스·manifest·서명은 함께 외부 보관한다. 폐쇄망 Docker 저장소 손상·이미지 삭제·서버 재설치 때 반입 원본이 필요하다.
- `backups/scheduled-release/<UTC>`는 업데이트 전 SQLite·PostgreSQL dump·설정/환경 파일·launcher·이전 이미지 참조를 보관한다 (`scheduled-release/apply.sh:102,110–116,198–214,249–259`). 일반 실행에는 필요 없지만 배포 성공만으로 복구 가치가 없어지는 것은 아니다.
- `$PREFIX/.koda-scheduled-last-backup`이 가리키는 최신 디렉터리를 삭제하면 기본 rollback은 실패한다 (`scheduled-release/rollback.sh:8–15`). 최신 복구 세트와 독립적인 검증된 전체 백업을 유지하고, 보존 기한이 지난 구형 세트부터 정리한다. 이동 시 pointer의 절대 경로와 롤백 이미지 태그도 함께 확인한다.
- 예약 릴리스 백업은 업로드 artifact·Dependency-Track 데이터까지 포함한 전체 백업과 다르다. 전체 복구는 suite 운영 문서의 별도 backup/restore 절차를 따른다.
- host `koda-suite/backups`와 Docker named volume `koda-sbom-backups`는 별개다. `data/koda-portal`, PostgreSQL·artifact·취약점 DB 등 실행 데이터 볼륨을 정리 대상으로 섞지 않는다.
- 파일 정리는 저장 공간을 회수한다. 점검·페이지 이동 속도 개선은 디스크 부족이 병목인 경우에만 기대할 수 있다. 이 판단은 현재 로컬 스크립트 기준이며 실제 서버의 파일 종류·마운트·이미지·백업 완전성은 확인하지 않았다. 삭제는 수행하지 않았다.
